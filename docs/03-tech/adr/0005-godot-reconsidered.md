# ADR-0005 — Godot reconsidered

- **Status:** Proposed — awaiting project lead
- **Date:** 2026-09-17
- **Revisits:** [ADR-0004](0004-engine-change-to-unreal.md), which superseded [ADR-0001](0001-engine-choice.md)
- **Question:** the presentation work is going badly. Is Unreal the reason?

## Why this is being asked

One day after moving to Unreal, progress on the presentation layer is poor. A single session
produced: a character posed by hand whose legs came out backwards, a climber who floated, an
invisible mesh that rendered an empty frame, an inspection command that silently rotated the thing
it was inspecting, and repeated cases of fixing one thing while breaking another. The project lead
asked whether Godot would simply work better.

This document is the evaluation. It is not a decision.

## What actually went wrong, separated honestly

Three different causes have been getting blamed on one thing.

**1. The feedback loop, not the engine.** Every judgement this session came from reading a single
static offscreen PNG. That loop misses everything that moves, shows one angle, costs three to four
minutes per look, and has been wrong repeatedly — a correct pose read as broken because the camera
command was spinning the subject; an empty frame read as a camera fault when the mesh was null.
This loop would fail identically in any engine. **Nobody has played this game yet.**

**2. Work done in the wrong half of the codebase.** ADR-0004 assigns ownership explicitly:

> Agents own `Source/SteeplejackSim/`, `data/`, `tools/`, `tests/` and `docs/` — all text, all
> diffable, all testable, all fast. […] Humans own `Content/` and `Source/SteeplejackGame/` —
> materials, lighting, Control Rig, Niagara, Chaos, scene assembly.

Essentially all of this session's agent work was in `Source/SteeplejackGame/` and `Content/`. The
half assigned to agents has gone fine throughout: 140 tests, ~1 second to run, no engine required,
no regressions. The half that has gone badly is the half the ADR predicted would go badly.

**3. Genuine Unreal friction.** Real and worth naming: ~3–4 minute rebuilds; binary assets that
cannot be read or diffed; silent failure modes that report success (hot-reload writing
`SteeplejackGame-0001.so` while `make play` loads the stale base `.so`; `duplicate_directory`
copying nothing and returning true; a null skeleton that asserts rather than warns).

Only the third is an argument about engines.

## What ADR-0004 already said about this

This was predicted, named and mitigated in advance:

> **Agent-executability**, which was the entire basis of ADR-0001. `.uasset` and `.umap` are
> binary; Blueprints are binary graphs. An agent cannot read or write any of it. Risk **R8**
> (editor work blocks the agent team) moves from medium to the top of the register.

R8 is now materialising exactly as written. That is not a surprise to be re-litigated; it is a
known accepted cost whose mitigation — the sim/presentation split — is in place and working.

## What ports, and what does not — measured

| | Lines | Ports to Godot? |
|---|---:|---|
| `Source/SteeplejackSim/` | 2,986 | **Yes, unchanged.** Verified engine-free: every include is standard library; the only mentions of Unreal are its README and `SteeplejackSim.Build.cs`, which exists solely to let UBT compile the same sources. |
| `tests/` | 2,926 | **Yes, unchanged.** doctest, CMake, no engine. |
| `data/`, `docs/`, `tasks/` | — | **Yes, unchanged.** Engine-agnostic by design. |
| `Source/SteeplejackGame/` | 2,880 | **No.** Rewritten. |
| `tools/editor/*.py` | part of 3,188 | **No.** UE Python editor scripting. |
| `Content/` | 10 assets | **No.** Regenerated by script, which is cheap — rule 3 means there is no hand-built content to lose. |

The sim layer holds ~100% of the gameplay logic and it is genuinely portable. GDExtension is the
supported route for C++ in Godot 4 and is actively maintained; integrating an existing C++ library
is a documented use case, not a research project.

**Position on the milestone map:** 18 of 69 tasks done, all still M0. ADR-0004's reversal table
gives "Now ~2 days (nothing is built)" and "After M1 ~3 weeks". We are near the cheap end —
realistically about a week, most of it re-doing the pawn, HUD, chimney generation and the editor
tooling.

## What Godot would genuinely fix

- **R8, directly.** `.tscn` is text. An agent can read, write, diff and review a scene. This is the
  single strongest argument and it addresses the actual top risk rather than a symptom.
- **Iteration speed.** GDScript reloads instead of a 3–4 minute C++ rebuild. The build-kills-editor
  dance disappears.
- **Automated testing in-engine.** gdUnit4 runs headless from the command line with JUnit XML out,
  which is a better story than the current in-editor automation tests.

## What Godot would cost

**The visual target, which is the entire reason for ADR-0004.** That requirement has not changed:
a photographed-looking brick chimney at close range, a mill town in haze, a sunset. ADR-0004's
judgement was "Godot will not reach it without a rendering programmer we do not have." Nothing in
this session bears on that judgement — the current flat look is because `ART-010` and `ENV-010`
have not been done, not because Unreal cannot.

**Four risks come back onto the register**, all of which ADR-0004 retired with named UE features:
Chaos Geometry Collections for felling (R3), Control Rig and Full Body IK for hand placement (R2),
MetaSounds for the tap test and height mix (R6), and Megascans for reading joint quality as a
close-range material (R1). Each becomes bespoke work again.

**One thing I got wrong and should correct:** I said in conversation that Godot ships no humanoid
and no locomotion animations, making a default walking character harder there. That is overstated.
Godot has no *built-in* mannequin, but free drop-in options exist — Quaternius's Universal Animation
Library (120+ animations, one rig, works in both engines) and GDQuest's Open 3D Mannequin with a
finite-state-machine controller. Character and locomotion are **not** a reason to stay.

## What Godot would not fix

I would still be the one building the presentation layer, still judging it from captures, and still
able to break the pawn while fixing the HUD. Faster iteration makes mistakes cheaper to find; it
does not make them less likely. If the loop stays "agent changes it, agent looks at a PNG, agent
declares it good", the same session repeats in Godot with shorter gaps between the errors.

## Two arguments raised after the first draft, both of which change the answer

**1. Agent competence is not engine-independent.** The project lead's hypothesis: there is far more
open-source Godot work to learn from than Unreal work. The premise holds, and the mechanism is
sharper than a repository count. The standard Unreal division is C++ for core systems and
**Blueprints for the gameplay layer** — and Blueprints are binary graphs. The precise layer an agent
most needs to imitate (how a character, camera and gameplay glue are actually assembled) is the
layer that cannot exist as text. Epic's reference project is account-gated, commercial UE titles are
never opened, and most UE knowledge is video. Godot is MIT, its engine and many complete small games
are readable, and both `.tscn` and GDScript are text.

The observed error profile matches: API knowledge was fine; *shape* knowledge was not. The worst
failure of the session was hand-writing a bone poser on a `PoseableMeshComponent` when `ACharacter`
plus the template's animation setup was the boilerplate answer. That is not a missing function, it
is a missing sense of what a normal project looks like.

**2. Less nuance means more progress.** Unreal offers many plausible-but-wrong paths where Godot
offers one: Pawn or Character; PoseableMesh or animation blueprint or Control Rig; setting a
movement mode per tick or on change; material usage flags you must already know to tick. Every
failure this session was a wrong fork taken where a standard existed. Unreal compounds it by
reporting success having done nothing — three separate times in one session.

**3. The flaw this exposes in ADR-0004.** Its mitigation for losing agent-executability is the
sim/presentation split, and that split assigns `Content/` and `Source/SteeplejackGame/` **to
humans**. There is no human doing Unreal presentation work on this project. The mitigation therefore
covers the logic layer and leaves uncovered the layer that is actually failing. ADR-0004 is
internally sound and rests on a staffing assumption that is false in practice. This is the single
strongest argument in this document and it was absent from the first draft.

## Recommendation

**Revised.** The first draft of this document recommended staying on Unreal. That recommendation
assumed agent effectiveness was roughly engine-independent and that ADR-0004's ownership split
described real labour. Both assumptions are wrong, so the recommendation changes.

**Move to Godot, if and only if the visual target can flex.** That condition is the whole decision
and it belongs to the project lead. ADR-0004 was not a mistake — it correctly optimised for "it just
needs to look great" and correctly priced agent-executability as the cost. What has changed is the
discovery that the cost falls on the only worker this project has.

- If the look is non-negotiable, stay on Unreal — and then the project genuinely needs a human doing
  the presentation layer, because that is what ADR-0004 says and it is not optional.
- If the look can become "good, readable, stylised, shipped", move. Roughly a week, and the sim,
  tests, data and docs — ~100% of the gameplay logic — come across untouched.

Either way, three things are true and worth doing first, because they are the causes that are not
about engines at all:

1. **Put a playable build in the project lead's hands.** This is the highest-value single change in
   the project right now, in any engine. Judgement moves from my reading of a frame to someone
   playing the thing.
2. **Respect ADR-0004's ownership line.** Agent work belongs in the sim, `data/`, `tools/`, `tests/`
   and `docs/`. Presentation work should be small, reviewed against a played build, and not
   attempted speculatively — the hand-written bone posing was exactly the kind of work this line
   exists to prevent.
3. **Make the silent failures loud.** Two are already fixed (`build-game` kills the editor and
   sweeps hot-reload leftovers; a missing mesh logs an error). The pattern — Unreal reporting
   success having done nothing — is the specific friction worth engineering against.

**Honest weight of the evidence.** One bad session is thin, and some of it was plain carelessness
rather than anything structural — asserting tool behaviour without running it, which is a recorded
recurring failure and would have cost the same in any engine. That argues for not over-reacting. It
does not rescue the staffing point, which stands independently of how well or badly the session
went.

The sim/presentation split means this option stays open and bounded. ADR-0004 called that property
"worth protecting even though we do not expect to use it again". It is doing its job today, one day
later, which is an unusually fast return on a piece of foresight.

## Consequences if accepted (move to Godot)

- ADR-0004 is superseded by a new ADR recording the move; ADR-0001's reasoning becomes live again
  for the premise it was given, which is the premise we are back to.
- The visual target in [`../../01-gdd/13-art-direction.md`](../../01-gdd/13-art-direction.md) is
  renegotiated in the same breath. Moving to Godot while holding "it just needs to look great" fixed
  would be choosing to fail at both.
- Budget ~1 week. The sim, tests, `data/`, `docs/` and `tasks/` carry over untouched;
  `Source/SteeplejackGame/`, `tools/editor/` and `Content/` are rewritten or regenerated.
- R1, R2, R3 and R6 return to the register and need owners.

## Consequences if rejected (stay on Unreal)

- ADR-0004 stands, and its ownership line becomes a staffing commitment rather than a diagram:
  someone human has to own `Content/` and `Source/SteeplejackGame/`.
- Agent work stays inside the sim, `data/`, `tools/`, `tests/` and `docs/`, and presentation tasks
  move to the `editor_required` queue rather than being attempted speculatively.
- The playable build is still the first thing to produce, for the same reason.
